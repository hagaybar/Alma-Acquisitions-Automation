1 · Follow the inputs and decisions

  1. Implemented code

    Existing invoices: Excel → payment attempts

    The bulk processor reads invoice IDs from the first Excel column. It fetches each invoice, skips terminal invoice or paid payment states, otherwise calls mark_invoice_paid(), fetches again, and writes results. There is no approval call in this path. Its success flag means the call returned, or the invoice was skipped; it does not require a final closed state.

    workflows/invoices/bulk_processor.py:182–294 · S1 · introduced 463a918

  2. Implemented code

    ERP rows + mapping → new invoices and linked lines

    The ERP path groups rows by invoice number, creates invoice headers, maps ERP orders to POLs, updates POL prices, and adds invoice lines. Missing mappings and price-update failures become errors. Optional payment calls approval then mark-paid. Grouping input rows is not evidence of protection against invoices already in Alma.

    Payment is attempted when requested and an invoice exists, even after line-processing errors. A failed line-helper return is not checked at its call site. This needs review before describing the path as an atomic end-to-end process.

    workflows/invoices/erp_integration.py:392–477, 518–546 · S2 · 463a918

  3. Implemented code

    Rialto invoice PDF → POLs → receive, pay, verify

    The pipeline extracts POL numbers from PDFs, optionally requests confirmation, and delegates to the workflow. Direct TSV input is also supported. It discovers an existing invoice; it does not create an Alma invoice from the PDF. Already received items skip receiving. Missing invoices skip payment.

    Discovery first uses the POL invoice reference, then searches selected invoice statuses, at most 100 results, matching invoice lines to the POL. The fallback has no explicit Rialto vendor filter and returns the first match. Receiving selects the first unreceived item, or the first item if all appear received.

    workflows/rialto/pipeline.py:300–394; workflows/rialto/workflow.py:85–139, 142–184, 280–339 · S3 · 463a918

    When unpaid, approval is attempted only for WAITING_TO_BE_SENT. Approval failure logs a warning and payment is still attempted. Payment failure continues to POL verification; live success is assigned from POL closure, so it can coexist with an earlier payment error. Dry-run success does not demonstrate a live transition.

    workflows/rialto/workflow.py:367–514 · S3

2 · Keep the state axes separate

Invoice status

Lifecycle of the invoice record, e.g. ACTIVE or CLOSED. Historical reports describe mark-paid producing closure.

Payment status

Payment recording, e.g. NOT_PAID or PAID. A mark-paid API operation is not independent evidence of an external funds transfer.

POL status

Purchase order line lifecycle, e.g. READY, SENT, CLOSED. A closed invoice can coexist with an open POL.

Historical transitions, not a universal state machine

docs/rialto_project_flow_findings.md:520–594, 650–700 · S4

The historical investigation proposes all items received, invoices paid/closed, a sent parent PO, and a one-time POL as closure conditions. It also records a POL remaining sent after receiving and invoice payment. These observations do not prove sufficient conditions for every tenant, configuration, or POL type.

5 · Questions to resolve at the meeting

  1. What exactly counts as complete?

    Require invoice CLOSED, payment PAID, POL CLOSED, all items received, and the expected department state? Decide which are mandatory and which require follow-up. Current paths check different subsets. S1 / S3

  2. Which invoices may be selected and paid?

    Confirm the Rialto selection rule, multi-invoice POL handling, multi-line invoice implications, pagination, and whether one item receipt may trigger paying an invoice covering other POLs. Current fallback returns the first matching invoice from a limited search. S3:85–139, 280–339

  3. Can we safely retry and recover partial failures?

    Review duplicate detection across invoices for the same POL, approval requirements, fail-closed behavior after approval errors, and recovery without recreating invoices. Historical safeguards live in the external library and need separate verification. S7:62–112; S2:437–475

  4. Which response fields and success signals are authoritative?

    Bulk code reads root payment_status; Rialto reads payment.payment_status. Bulk declares success before confirming final states; Rialto success comes from the POL even after a payment error. Agree on response schema and outcome assertions before a future sandbox validation. S1:246–287; S3:425–514

  5. What still needs a controlled sandbox demonstration?

    Tenant closure conditions, parent PO readiness, all-item receiving, already-paid invoices, missing/multiple links, approval failures, and final invoice/POL states. Existing integration scripts are hand-run operational artifacts, excluded from pytest; their presence proves no current pass. pyproject.toml:24–28 · 817e9ad. This is a proposed agenda, not authorization to execute it.
